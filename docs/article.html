Inside AUTHENTIX: Building an Automated BOLA & IDOR Detection Engine for Burp Suite using the Montoya API

Why legacy HTTP proxies fail at access control, deterministic finite-state automation, cross-actor matrix verification, and 27 formal security invariants.
By Pratik Khairnar • AppSec & Security Researcher • 14 min read • Oct 2026

1. The Crisis of Modern Access Control

According to the OWASP Top 10 API Security Risks, Broken Object Level Authorization (BOLA / IDOR) and Broken Authentication consistently rank as the most prevalent and catastrophic vulnerabilities in modern cloud applications. While modern application stacks have largely mitigated classic injection vectors through parameterized Object-Relational Mappings (ORMs) and modern reactive frameworks with contextual output encoding, access control vulnerabilities have proliferated exponentially. 

+-------------------------------------------------------------------------+
|                      The Modern AppSec Paradox                          |
|                                                                         |
|   Memory Safety / Injections                 Access Control (BOLA/IDOR) |
|   ==========================                 ========================== |
|   [ Rust / Go / Parameterized ORMs ]         [ Business Logic Blindness ]
|   • SQLi -> Drastically Reduced              • BOLA/BFLA -> Exponential Spike
|   • Buffer Overflow -> Rare in Web           • Multi-Step Auth Bypass -> Rising
|   • Reflected XSS -> Framework Guarded       • Complex State Chains -> Unchecked
+-------------------------------------------------------------------------+

The fundamental reason is architectural: access control is inherently semantic. A compiler, static linter, or traditional web application firewall (WAF) cannot intuitively understand whether user tenant_492 is authorized to mutate the billing configuration of tenant_811. To an automated proxy or signature-based scanner, both HTTP requests look structurally identical: valid headers, proper JSON syntax, and authenticated session tokens.

For the past decade, penetration testers and AppSec engineers evaluating access control inside PortSwigger Burp Suite relied on manual Repeater tampering or legacy extensions built on the aged IBurpExtender interface. These approaches suffer from severe systemic limitations:

  • Stateless Request Blindness: They inspect single HTTP request/response pairs in complete isolation, oblivious to the state transitions occurring across an actor's lifecycle.
  • Actor Disconnect: They lack an automated concept of multi-actor ownership (distinguishing between Actor A, Actor B, and Unauthenticated actors across thousands of transactional endpoints).
  • High Latency & UI Freezes: Legacy extensions executing synchronous network requests frequently lock Burp Suite's Java Swing Event Dispatch Thread (EDT).

To solve this, I designed and implemented AUTHENTIX v2.1.0—an enterprise-grade security extension built natively on PortSwigger's modern Montoya API in Java 17/21. In this architectural deep dive, we will dissect how AUTHENTIX replaces ad-hoc regex heuristics with Deterministic Finite-State Automata (DFA), enforces 27 formal mathematical security invariants, maintains a real-time Cross-Actor Authorization Matrix, and synthesizes compound Account Takeover (ATO) kill chains.

2. Why Legacy HTTP Proxies Fail at Access Control

To understand why automated BOLA detection requires a new architectural model, consider how a traditional HTTP proxy extension processes traffic:

                                                                      │
                                                           Rampant False Positives
                                                           or Total False Negatives

In the legacy IBurpExtender paradigm, an extension registers an IHttpListener. When a request is handled, the callback receives an isolated IHttpRequestResponse object. This model collapses when faced with modern distributed architectures:

A. The Loss of Temporal and Conversational Context

Web applications are state machines. A session token transmitted in a request was generated before login, during the MFA challenge phase, or after an explicit logout call. If an application fails to invalidate a pre-auth session cookie upon authentication (a classic Session Fixation vulnerability), a stateless proxy will never catch it because both requests appear independently benign.

B. The Actor Attribution Problem

Detecting BOLA requires establishing a mathematical relationship between three entities:

  1. The Subject: The authenticated identity (Actor A: token τA, user identifier UIDA).
  2. The Target Resource: An object identifier (ResB) owned by an independent identity (Actor B).
  3. The Operation: The HTTP method and route (GET /api/v1/invoices/Res_B).

4. Deterministic Finite-State Automata (DFA) for Auth Lifecycles

Rather than guessing if an endpoint is vulnerable, AUTHENTIX mathematically monitors state transitions using a formal Deterministic Finite-State Automaton. We formally define the actor authentication lifecycle as a 5-tuple:

M = (Q, Σ, δ, q0, F)

Where:

  • Q = { q_UNAUTH, q_PREAUTH, q_MFA_PENDING, q_AUTHENTICATED, q_TERMINATED } is the finite set of valid actor states.
  • Σ = { e_GET_LOGIN, e_POST_CREDS, e_CHALLENGE_ISSUED, e_SUBMIT_OTP, e_API_CALL, e_POST_LOGOUT, e_PW_RESET } is the input alphabet.
  • δ : Q × Σ → Q is the state transition function.
  • q_0 = q_UNAUTH is the initial start state.
  • F = { q_TERMINATED } is the set of accept/terminal states.

5. The Cross-Actor Authorization Matrix Engine

The crown jewel of AUTHENTIX is its Cross-Actor Authorization Matrix. To detect BOLA/IDOR with near-zero false positives, the engine maintains distinct actor profiles observed during a testing session:

  • Actor A (Primary Tester / Low Privilege): Token τA, Identifiers { IDA1, IDA2 }
  • Actor B (Secondary Victim / Peer Privilege): Token τB, Identifiers { IDB1, IDB2 }
  • Unauthenticated Actor: No session context (τ∅)

Response Equivalence & Structural Differential Analysis

A naive status code comparison (200 OK) is insufficient. Many modern Single Page Applications return 200 OK with generic error envelopes like {"success": false, "error": "Access Denied"}. To eliminate false positives, AUTHENTIX executes Structural JSON Differential Analysis: 

public boolean isAuthorizedAccessConfirmed(HttpResponse originalResponse, HttpResponse probeResponse) {
    if (probeResponse.statusCode() != 200) {
        return false;
    }

    // Levenshtein / Normalized Compression Distance (NCD) check
    byte[] originalBody = originalResponse.body().getBytes();
    byte[] probeBody = probeResponse.body().getBytes();
    double structuralSimilarity = calculateNCD(originalBody, probeBody);

    // Negative pattern guard (anti-soft-200)
    String bodyStr = probeResponse.bodyToString().toLowerCase();
    for (String indicator : SOFT_403_PATTERNS) {
        if (bodyStr.contains(indicator)) {
            return false;
        }
    }

    // If similarity > 0.85 and no soft-403 strings, cross-actor leakage is confirmed
    return structuralSimilarity > 0.85;
}

9. Architectural Defense: Remediating BOLA in Enterprise Code

How should engineering teams eliminate BOLA/IDOR permanently? Access control must be enforced at the repository or query level by enforcing a tenancy boundary: 

# ✅ SECURE: The logged-in user identity is bound directly to the database query
@app.route("/api/v2/accounts/<account_id>", methods=["GET"])
@require_authenticated_user
def get_account(account_id):
    current_user_id = g.current_user.id
    
    # Query enforces that the account MUST belong to the requesting tenant
    account = db.query(Account).filter(
        Account.id == account_id,
        Account.tenant_id == current_user_id
    ).first()
    
    if not account:
        abort(404, description="Resource not found")
        
    return jsonify(account.to_dict())
